# FR3 SpaceMouse-request alignment — offline diagnostic only

The original 100-episode raw captures contain two RGB views, measured FR3
and Robotiq states, 100 Hz SpaceMouse Twist request messages and sparse
button-driven gripper requests. Their `training_action` fields are `null`.

`toolkits.realworld_check.fr3_command_request_alignment` makes a *new*,
provenance-rich JSONL candidate dataset by time-aligning these saved ROS
requests to successive observation-camera receipt windows. No ROS node,
controller, camera or robot is accessed. The raw dataset is read only.

## Run on the lab PC

```bash
cd ~/Desktop/AIST-Tokyo/gamma/rlinf-project
git pull --ff-only origin branch-openpi-recap-franka
python -m pytest -q tests/unit_tests/test_fr3_command_request_alignment.py
python -m toolkits.realworld_check.fr3_command_request_alignment \
  --raw-root /data1/Muttaqien/fr3_peg_100 \
  --output /data1/Muttaqien/fr3_peg_command_request_candidate_v1 \
  --expected-episodes 100
```

This creates only the new output directory (refuses overwrite) containing
`report.json` and one `episodes/episode_*.jsonl` file per capture.
Images are referenced by relative path under the ORIGINAL episode and are
not copied. The JSONL rows carry 19D candidate observations, a 6D
**time-weighted normalized request** and the last latched binary gripper
button request, or `null` until one is observed. Windows with stale
twist data, missing grip state, invalid time deltas or insufficient coverage
receive `candidate_request_action_7d: null`.

The default 100 ms maximum Twist age and 90% valid time coverage are
*diagnostic thresholds*, not calibrated control-loop timing. Camera receipt
timestamps are NOT necessarily exposure timestamps or accepted-command times.
The 6D window average is not identical to how a high-frequency controller
applies its latest request. The seventh scalar is a button request, NOT a
Robotiq target joint value or measured aperture.

**No controller execution or acceptance is established** by the presence
of ROS messages, even when the count of dropped recorder messages is zero.
The inspected C++ controller converts each received normalized Twist into
a relative pose update, repeatedly used by its update loop. The exact
translation frame, orientation convention, update rate, command latency,
and gripper bridge need independent verification before choosing a policy
action interface. The previously noted controller version reportedly uses
0.007 for linear scaling and 0.06 for rotation; do not assume stored
requests are SI velocities or pose deltas.

## Remaining gates

1. Inspect the aggregate per-episode coverage, timestamp gaps, null labels,
   gripper changes and source motion versus requests.
2. Verify controller code, deployed configuration, frames, control rate,
   topic timestamps, gripper bridge and robot-response latency.
3. Freeze a **separate** command-request OpenPI training contract, 7D
   representation, normalization and split. The existing proxy dataset,
   normalizers and π₀.₅ proxy-trained checkpoint are not substitutes.
4. Before RECAP, obtain real rollout outcomes and a compatible critic/CFG
   transform; neither is generated by this alignment tool.
